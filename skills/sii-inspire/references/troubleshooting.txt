# Troubleshooting — SII 启智平台

## Task Stuck in "Creating" (创建中) for >30 min

| Cause | How to identify | Fix |
|-------|----------------|-----|
| Image pull slow | Image >20GB, target node has no cache | Wait ~20 min, or optimize image size |
| Image not found | Wrong image name/tag, or image not registered on platform | Check `inspire_images` for registered images. After push, must register via 镜像管理 → 新建镜像 |
| Wrong display domain | Used push domain (docker-qb.sii.edu.cn) instead of display domain (docker.sii.shaipower.online) | Always use platform-assigned display domain in task submission |
| Node fault | Target node has disk failure or is NotReady | Contact ops with task ID |

## Task Stuck in Queue (排队中)

| Cause | How to identify | Fix |
|-------|----------------|-----|
| Resources full | All GPUs in the compute group occupied | Wait or switch compute group |
| Node taints | Nodes have ECC errors, RDMA faults, GPU failures | Contact ops with task ID + node name |
| Multi-node task | Needs N nodes simultaneously free | Smaller tasks get scheduled first; try off-peak hours |
| Priority too low | Priority 1-3 waits behind ≥4 | Use higher priority if budget allows |
| RDMA insufficient | Multi-GPU needs RDMA, some nodes lack it | Contact ops |

Diagnosis steps:
1. `inspire_status` → check free GPUs in target compute group
2. Free GPUs exist but still queued → likely node taints. Contact ops.
3. Queued >24h → switch compute group or contact ops

## Task Killed Unexpectedly

| Cause | How to identify | Fix |
|-------|----------------|-----|
| Priority preemption | Priority 1-3, killed when resources tight | Use priority ≥4 |
| GPU utilization low | Auto-reclaimed by platform policy | Ensure GPU is actively used during training |
| OOM (CPU memory) | "Killed" in logs, dmesg shows oom-killer | Reduce batch size or request more memory |
| OOM (GPU memory) | "CUDA out of memory" in logs | Reduce model/batch size, enable gradient checkpointing |
| Budget exhausted | `inspire_status` shows budget ≤0 | Wait for refresh or use low-priority CPU tasks |
| Terminal disconnected | Interactive task without tmux/nohup | Use: `nohup python train.py > log.txt 2>&1 &` |

## spec_id Issues

### "spec_id not found in workspace predef_train_spec"
- The spec_id doesn't belong to the target workspace+compute group
- Different compute groups have different spec lists
- Specs can expire when platform updates configurations
- Fix: omit `spec` parameter → tool shows current available specs. Pick the right one.

### "record not found" when creating notebook
- Notebook specs (SCHEDULE_CONFIG_TYPE_DSW) differ from training specs (SCHEDULE_CONFIG_TYPE_TRAIN)
- A training spec_id cannot be used for notebook creation
- Fix: omit `spec` when calling `inspire_notebook(action="create")` to see notebook-specific specs

## Image Issues

### "image not found" when submitting task
1. Image not registered on platform → register via 镜像管理 → 新建镜像
2. Using push domain instead of display domain → use docker.sii.shaipower.online/... (not docker-qb.sii.edu.cn/...)
3. Image registered in wrong registry → SJ space needs docker-t.sii.shaipower.online, all other spaces need docker.sii.shaipower.online

### Image push fails with "Unavailable" or "unknown error"
- Most likely cause: Robot account lacks push permission for the target repository
- Less likely: Harbor service temporarily down or network issues
- Harbor supports auto-creating repositories on push — pre-creation is NOT needed
- Temporary workaround: `docker save` to .tar file, upload via platform UI

### Image push succeeds but not visible on platform
Push to Harbor is not enough. Must register: 镜像管理 → 新建镜像 → fill 镜像名称 + 版本号 → save.

### Image save stuck or failed
- Image >100GB may fail; clean caches first: `apt clean && pip cache purge && rm -rf ~/.cache`
- Saving pauses the container (processes resume after save completes)
- Stuck >1 hour: likely failed. Contact ops with instance ID.

## Command Execution Errors

### `conda activate` fails
Non-interactive shell doesn't load `.bashrc`. Fix:
```bash
source /opt/conda/etc/profile.d/conda.sh && conda activate myenv
```
Find conda path: `which conda` → e.g., `/root/miniconda3/bin/conda` → init at `/root/miniconda3/etc/profile.d/conda.sh`

Tip: write the full env init explicitly in every command. Do NOT set `commandPrefix` — see the main skill's "First-Time Setup" section for why (Synergy-wide global breaks multi-project setups).

### `uv: not found` / `poetry: not found` / `pip: not found`
PATH not set in non-interactive shell. Fix:
```bash
export PATH="$HOME/.local/bin:$PATH"
```

### `pip install` fails in offline space
Offline spaces (分布式训练空间, 高性能计算, 整节点任务空间) have NO internet. Solutions:
1. Pre-install in the Docker image (build in online space, save, use in offline space)
2. Use Nexus mirror: `pip install -i http://nexus.sii.shaipower.online/repository/pypi_proxy/simple/ --trusted-host nexus.sii.shaipower.online <package>`

### Disk quota exceeded
- Check: `df -h /inspire/hdd/project/{name}/`
- Project quota: contact advisor
- Personal quota: Feishu → 审批 → 算力平台存储申请
- Workaround: clean unused data, use `global_user` directory

## nvidia-smi Issues

### GPU list empty (only header, no devices)
Node GPU hardware fault. Contact ops with instance ID and node name.

### Memory occupied but utilization 0%
Zombie process or deadlock. Try `kill -9 <PID>`. If unkillable, contact ops.

## Authentication Issues

### "您已离开所选项目"
The project_id in the request doesn't match any project you're currently a member of. Use `inspire_status` to see your current projects and their IDs.

### API 权限未开通
Your account may not have API access. Contact platform administrator to enable it. Check under 个人中心 → API 管理.

## Failure Auto-Retry Protocol

When an experiment fails, don't just report it — attempt automated diagnosis and recovery before escalating. The table below summarizes the recognized failure classes and the recovery actions.

### Recognized failure classes

| Class | Detection | Auto-recovery | Max retries | Escalate when |
|-------|-----------|---------------|-------------|---------------|
| **OOM (GPU)** | `CUDA out of memory`, `Killed` in log | Halve `batch_size`, double `gradient_accumulation_steps` | 2 | bs would drop below 1, or OOM persists at bs=1 |
| **NaN / Inf loss** | `nan`, `inf`, `loss is NaN`, `diverged` in log | LR ×0.1, enable `max_grad_norm=1.0`, enable dynamic loss scale | 2 | Still diverges (likely method/code bug, not HP) |
| **Preempted** | Job status `stopped` not by user, logs end mid-training | Resume from latest checkpoint; if none, resubmit at higher priority | unlimited while progress | Preempted 3+ times (queue too contested) |
| **Stale process** | GPU util < 10% for > 15 min, no log for > 10 min | `inspire_stop` + kill + resubmit | 1 | Stalls again on retry (data pipeline deadlock) |
| **Import error** | `ModuleNotFoundError`, `ImportError`, `conda: command not found` | Fix env init in command (check `source conda.sh`, image, offline deps) | 1 | Package truly missing in image → rebuild image |
| **Data path error** | `FileNotFoundError`, `No such file or directory` for data | Check `ASSETS.md` / project en_name in path; fix and resubmit | 1 | Data actually doesn't exist on platform → need to upload |
| **Image / GPU mismatch** | Immediate CUDA errors, `no CUDA-capable device`, driver mismatch | Switch to correct compute group from `inspire_status`; rebuild image if CUDA ver wrong | 1 | No compatible GPUs available anywhere |

### Protocol rules

1. **Max 2 automatic retries per failure type** per experiment. After that, escalate.
2. **Each retry is a NEW experiment record** — don't overwrite the original. Link via notes.
3. **Record failure reason** on the original experiment:
   ```
   research_experiment(action="fail", id="exp_007",
     failure_reason="OOM at step 8000, batch_size=128")
   ```
4. **Record retry link** in the new experiment's notes:
   ```
   Retry of exp_007 — reduced batch_size 128 → 64
   ```
5. **Never retry silently** — append to research_timeline:
   ```
   research_timeline(action="append_free_event", event_type="decision",
     summary="Auto-retry exp_007 → exp_008 (bs 128 → 64 due to OOM)",
     event_refs=["exp_007", "exp_008"])
   ```

### Escalation format

When auto-recovery fails or the failure class is unknown:

```
⚠️ Experiment exp_XXX failed and auto-recovery was unsuccessful.

Failure class: [OOM / NaN / preempt / stale / import / data / image / unknown]
Attempts:      [N]
Last error:    [exact log excerpt]

Recommended next step:
  - [specific action for this failure class]
  - Method-level issue → consider rollback to spec phase
  - Infrastructure issue → check platform status / image / data path
```

### Participation mode behavior

Different Synergy modes treat auto-retry differently:

- **collaborative**: Report every failure, ASK before retrying
- **guided**: Auto-retry OOM / preempt silently, report other classes
- **autonomous**: Auto-retry all known classes, escalate only unknowns and after 2+ retry exhaustion
